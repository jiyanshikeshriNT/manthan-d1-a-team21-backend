# ReturnRight — Low-Level Design

## 1. Containers and modules
- **Containers (Compose):** `app` (Spring Boot portal plus in-process gateway-mock), `postgres:17`, `prometheus`, `grafana`. Photos are stored in a volume mounted at `/data/photos`.
- **Gradle:** root `system` (portal, bootJar), `gateway-api` (java-library), `gateway-mock` (java-library with Spring auto-configuration, own `gw_` tables, own Flyway location `classpath:db/migration/gateway`).
- **Portal modules** (packages under `com.example.customer_retail_system.system`):
  - `catalog`: categories and products.
  - `customer`: customers and flags.
  - `order`: order lookup.
  - `eligibility`: pure rules engine.
  - `returns`: aggregate, state machine, label/QR, photos.
  - `inspection`: warehouse actions.
  - `refund`: orchestration, reconciler, finance actions.
  - `ledger`: double-entry ledger.
  - `audit`: append-only log.
  - `dashboard`: read models.
  - `security`: staff auth, customer tokens, rate limiter.
  - `shared`: errors, Clock, money.
  - `seed`: `seed`-profile demo data (deterministic `SeedDataGenerator` + `SeedDataLoader`, plain JDBC,
    one transaction, no-op when any core data exists). Depends only on `shared`.
- Entities and repositories live in each module's `internal` package; modules reference each other's
  rows by id only (e.g. `order_line.product_id`, `customer_order.customer_id`), never by JPA association.
- JVM default zone is pinned to UTC (`SystemApplication.main`, test JVM); timestamps are stored as
  `TIMESTAMP WITH TIME ZONE`; business dates use the injected `Clock` in `app.zone` (Asia/Kolkata).

## 2. Database schema
Flyway `V1__core.sql`, `V1_1__customer_access_token.sql` (Phase 3; numbered 1.1 so V2/V3 keep their
meaning), `V2__returns.sql`, `V3__refund_ledger_audit.sql`; gateway `V100__gateway.sql`.

| Table | Key columns / constraints |

| `product` | id PK, sku UNIQUE, name, category_id FK, price_paise BIGINT |
| `customer` | id PK, email UNIQUE (stored lower-case), name, phone, created_at |

| `return_request` | id UUID PK, rma_number UNIQUE, order_id FK, customer_id FK, status, refund_method, flagged BOOL, label_code UNIQUE, client_request_key UNIQUE NULL (Idempotency-Key header), total_refund_paise BIGINT NULL, created_at, updated_at, closed_at, version; IDX(customer_id, created_at), IDX(status) |

| `refund` | id PK, return_id UNIQUE FK, amount_paise, method, status (PENDING, AWAITING_APPROVAL, PROCESSING, UNKNOWN, SUCCEEDED, FAILED, REJECTED), idempotency_key UNIQUE, gateway_txn_id, attempts, requires_approval, approved_by, approved_at, last_error, next_attempt_at, created_at, updated_at, version |
| `ledger_entry` | id PK, refund_id FK, customer_id, account (REFUND_EXPENSE, GATEWAY_CLEARING, STORE_CREDIT_LIABILITY), direction (DEBIT/CREDIT), amount_paise > 0, created_at; UNIQUE(refund_id, account, direction) |
| `audit_log` | id PK, entity_type, entity_id, action, from_state, to_state, actor, actor_role, details TEXT, correlation_id, created_at; IDX(entity_type, entity_id) |
| `gw_payment` (gateway module) | id PK, idempotency_key UNIQUE, amount_paise, reference, status, txn_id, created_at |

**V1 constraints (as implemented):** ids are `BIGINT GENERATED BY DEFAULT AS IDENTITY`; timestamps are
`TIMESTAMP WITH TIME ZONE`. CHECKs: `category.return_window_days > 0` (or NULL), `product.price_paise >= 0`,
`customer.email = LOWER(email)`, `customer_order.payment_method IN (CARD, UPI, NETBANKING, WALLET)`,
`delivered_at >= ordered_at`, `order_line.quantity > 0`, `order_line.unit_price_paise >= 0`,
`staff_user.role IN (WAREHOUSE, FINANCE, MANAGER)`. Extra indexes: `product(category_id)`, `order_line(order_id)`.

**V2 (as implemented, Phase 4):** also creates `audit_log` (moved here from V3 because every return
transition is audited from Phase 4; `details` is `VARCHAR(2000)` rather than TEXT so H2 and PostgreSQL map
it identically) and `rma_number_seq` (RMA numbers `RMA-{n}` from 100001, read with `nextval('rma_number_seq')`).
`return_item` has UNIQUE(return_id, order_line_id); CHECKs mirror the enums (status, refund_method,
reason_code DAMAGED/DEFECTIVE/WRONG_ITEM/WRONG_SIZE/NOT_AS_DESCRIBED/CHANGED_MIND/OTHER, grade A/B/C,
decision ACCEPTED/REJECTED, `0 <= accepted_qty <= requested_qty`, photo type JPEG/PNG and size ≤ 5 MB).
`client_request_key` stores `{orderId}:{Idempotency-Key}` so keys are scoped per order.

**Seed data set (`seed` profile, `app.seed.random-seed`):** 6 categories (ELECTRONICS 10 days; APPAREL,
HOME, BEAUTY 30 days; INNERWEAR, PERISHABLES not returnable), 40 products (electronics priced on both sides
of ₹10,000), 500 customers, 2,000 orders `ORD-100001…ORD-102000` delivered 0–60 days ago (every day
present, so 10/11 and 30/31 boundaries exist; every 25th order undelivered), staff users `warehouse`,
`finance`, `manager` sharing `app.seed.staff-password` (BCrypt).

**Ledger postings per refund (balanced):**
- Original payment: DEBIT REFUND_EXPENSE / CREDIT GATEWAY_CLEARING.
- Store credit: DEBIT REFUND_EXPENSE / CREDIT STORE_CREDIT_LIABILITY (keyed by customer).

## 3. Core flows
1. **Lookup:** `POST /customer/session` checks the rate limit, matches order number and lower-cased email, and returns a token. Any miss returns 404 `ORDER_NOT_FOUND` with generic copy.
2. **Create return:** multipart request + photos with an `Idempotency-Key` header. Lock the order, run eligibility per line (fail the whole request if any selected line is ineligible, listing the reasons), store photos, compute the flag, insert the return in REQUESTED, then transition to APPROVED or PENDING_REVIEW. Generate the label code and HMAC. Audit runs in the same transaction. Replaying the same key returns the original response.
3. **Ship:** APPROVED → IN_TRANSIT.
4. **Warehouse:** look up the return by label (verify HMAC), RECEIVED, then inspection (per-item grade, decision and acceptedQty) → INSPECTED. Compute item refunds and the total. If total = 0, go to REJECTED. Otherwise create the refund: total > 10k → AWAITING_FINANCE (refund AWAITING_APPROVAL), else → REFUND_IN_PROGRESS and execute.
5. **Refund execution (RefundExecutor):**
   - tx1: `UPDATE refund SET status='PROCESSING', attempts=attempts+1 WHERE id=? AND status IN ('PENDING','UNKNOWN')`. If 0 rows are updated, return the current state with no gateway call.
   - Outside any transaction: `gateway.pay(key, amount, ref)` with a 3 s timeout.
   - tx2 on success: refund SUCCEEDED, ledger pair, return REFUNDED, closed_at, audit, metrics.
   - On timeout or 5xx: UNKNOWN with `next_attempt_at` set by backoff.
   - On a definite decline: FAILED, then alert and audit.
6. **Reconciler (`@Scheduled` every 30 s):** picks refunds in UNKNOWN, or PROCESSING for more than 2 min. It calls `gateway.status(key)`: found leads to SUCCEEDED, not found re-runs `pay` with the same key. After 5 attempts the refund goes to FAILED, and finance can retry it manually with the same key.
7. **Finance:** approve leads to execution. Reject (reason required) sets refund REJECTED and the return REJECTED. Both use conditional updates, so a double approval is a no-op that returns the current state.

## 4. API contracts (`/api/v1`, JSON, errors as ProblemDetail + `code`)
| Role | Method & path | Notes |
|---|---|---|
| public | POST `/customer/session` {orderNumber,email} → {accessToken,expiresAt} | 429 RATE_LIMITED, 404 ORDER_NOT_FOUND |
| customer | GET `/customer/orders/{orderNumber}` → lines + `eligibility{eligible, code, message, returnableQty, deadline}` | |
| customer | POST `/customer/returns` multipart(`request` JSON {orderNumber, refundMethod, items[{orderLineId, qty, reasonCode, reasonText}]}, `photos_{orderLineId}`) → 201 {rma, status, labelCode, timeline} | 422 ITEM_NOT_RETURNABLE (per-item reasons), 400 PHOTO_INVALID |
| customer | GET `/customer/returns/{rma}` → status + timeline[{step, state: done/current/pending/failed, at}] | |
| customer | GET `/customer/returns/{rma}/label` (JSON) and `/label/qr.png` | |
| customer | POST `/customer/returns/{rma}/ship`, `/cancel` | 409 INVALID_TRANSITION |
| warehouse | GET `/warehouse/labels/{labelCode}`; POST `/warehouse/labels/decode` (QR image → code) | 400 LABEL_INVALID |
| warehouse | GET `/warehouse/returns/{rma}`; POST `/warehouse/returns/{rma}/receive`; POST `/warehouse/returns/{rma}/inspection` {items[{itemId, grade, decision, acceptedQty, note}]} | 404 RETURN_NOT_FOUND |
| finance | GET `/finance/refunds?status=`; GET `/finance/refunds/{id}` (detail); POST `/finance/refunds/{id}/approve`, `/reject` {reason}, `/retry`; GET `/finance/ledger?from&to` | 404 REFUND_NOT_FOUND |
| manager | GET `/manager/dashboard?from&to`; GET `/manager/reviews`; POST `/manager/reviews/{rma}/approve`, `/reject`; GET `/manager/audit?entityId=` | |
| manager | GET, PUT `/admin/gateway/faults` {mode, latencyMs} | non-prod only |
| staff (any role) | GET `/staff/me` → {username, role} | 401 bad credentials; lets the web portal verify a sign-in |

**Web portal support (frontend integration):**
- `GET /staff/me`: any staff role; the portal calls it with the Basic credentials before storing them.
- `GET /warehouse/returns/{rma}`: the WarehouseReturnView by RMA (reload after a conflict, typed RMA).
- `GET /finance/refunds/{id}` → `{refund (RefundView), returnId, rma, orderNumber, returnStatus, flagged,
  flagReason, requestedAt, items[{itemId, sku, productName, requestedQty, unitPricePaise, reasonCode, reasonText,
  photoCount, conditionGrade, decision, acceptedQty, refundPaise, inspectionNote}]}`.
- Customer return items also carry `sku, productName, unitPricePaise, conditionGrade, decision, acceptedQty,
  refundPaise` (inspection fields null until inspected), and the return carries `totalRefundPaise`.
- Dashboard categories carry `returnable` (category policy).
- CORS is off by default (the Vite dev server proxies `/api`); set `app.cors.allowed-origins` (comma-separated)
  when the portal is served from another origin.

**Customer returns API details (Phase 4):**
- Create: `Idempotency-Key` is optional (1–100 chars), scoped per order; a replay returns 201 with the
  original return and header `Idempotent-Replayed: true`. Photo parts `photos_{orderLineId}`, ≤ 3 per item,
  only for items in the request. `reasonText` is required when `reasonCode` = OTHER.
- 422 `ITEM_NOT_RETURNABLE` carries `items[{orderLineId, code, message}]` for every refused line; besides the
  eligibility codes, `QUANTITY_EXCEEDED` = "Only {n} units of this item can be returned." Nothing is created.
- Flagging counts the customer's requests with `created_at` in the last `app.flagging.window-days`, status ≠
  CANCELLED, plus the new one; > `app.flagging.max-requests` ⇒ PENDING_REVIEW + `customer_flag` row.
  `flagged` is never exposed to the customer.
- Return body: `{rma, orderNumber, status, statusLabel, refundMethod, labelCode, createdAt, totalRefundPaise,
  items[], timeline[]}`.
  `labelCode` is null (and `/label`, `/label/qr.png` answer 409) unless status ∈ APPROVED…REFUNDED.
  Label code = `RR-{rma}-{first 8 hex of HMAC-SHA256(app.label.secret, rma)}`; QR is a 300 px PNG, `no-store`.
- Timeline: six steps Requested, Approved, In transit, Received, Inspected, Refunded, built from the audit
  log (`at` = first time each step was reached). PENDING_REVIEW → Requested/current, note "Under review";
  AWAITING_FINANCE / REFUND_IN_PROGRESS → Inspected/current, notes "Awaiting refund approval" / "Refund
  processing". REJECTED/CANCELLED → the steps reached, then a final `failed` step with the reason.
- Ship/cancel repeated in the same target state are no-ops (200, no audit row); illegal moves → 409
  `INVALID_TRANSITION` with customer copy and `currentStatus`.
- Audit: `audit.AuditLog.record` is `Propagation.MANDATORY` (same transaction as the change), details are
  PII-masked (`shared.PiiMasker`), actor = `customer:{id}` / `system` / `staff:{username}`.

**Warehouse, refund, finance and manager details (Phases 5–7):**
- `POST /warehouse/returns/{rma}/receive` accepts an optional body `{labelCode}`; if given it must verify and
  belong to `{rma}` (400 `LABEL_INVALID` otherwise). Re-scanning a RECEIVED return is a no-op.
- `POST /warehouse/labels/decode` takes multipart part `image` and returns `{labelCode, rma}`.
- Inspection must cover every item exactly once; `acceptedQty` defaults to the requested quantity for
  ACCEPTED and must be 0/absent for REJECTED. Item refund = `Money.percentOf(unitPrice × acceptedQty, grade%)`.
  Responses include the item verdicts, `totalRefundPaise` and the `refund` (RefundView) once created.
- The inspection commits first; an auto-approved refund is executed afterwards, outside any transaction
  (`RefundExecutor` refuses to run inside one). Finance approve/retry do the same.
- Refund statuses PENDING → PROCESSING → SUCCEEDED | UNKNOWN | FAILED; AWAITING_APPROVAL → PENDING (approve)
  | REJECTED. Finance retry: FAILED → PENDING (attempt counter reset, same key); UNKNOWN/PENDING executed as is.
  Approve/reject: repeat of the same decision is a no-op; the losing one of a race gets 409 with `currentStatus`.
- Reconciler (`app.refund.reconcile-interval-ms`, off in tests) handles UNKNOWN when `next_attempt_at` is due,
  and PENDING/PROCESSING untouched for `app.refund.stuck-after` (2 m). It asks `status(key)` first; failed
  status checks also count as attempts (backoff `app.refund.initial-backoff` × 2^(n−1), max 10 min); after
  `app.refund.max-attempts` (5) the refund is FAILED. Gateway timeout `app.refund.gateway-timeout` (3 s).
- Audit rows for refunds use entity type `REFUND` and the refund id; gateway fault changes use `GATEWAY/faults`.
- `GET /finance/refunds?status=` (all when omitted); `GET /finance/ledger?from&to` → `{entries, totalDebitPaise,
  totalCreditPaise, balanced}`; dates are inclusive in Asia/Kolkata, default the last 30 days, max 366 days.
  Unknown refund id → 404 `REFUND_NOT_FOUND`.
- Gateway port also defines an optional `GatewayFaultControl` (implemented only by the mock) so the non-prod
  `GET/PUT /admin/gateway/faults` endpoint and tests never import mock classes. Fault modes: NONE, FAIL,
  TIMEOUT, SLOW, FAIL_AFTER_CHARGE and **DECLINE** (added to exercise the definite-decline path).
- `gw_payment` comes from `db/migration/gateway/V100__gateway.sql`, found by the portal's recursive Flyway scan;
  `spring.flyway.out-of-order=true` lets future portal versions (V4+) apply after V100.
- V3 also adds the dashboard indexes: customer_order(ordered_at), return_request(created_at), (closed_at),
  customer_flag(cleared_at, customer_id), plus audit_log(entity_id), (created_at).
- Manager reviews: `GET /manager/reviews` → `[{returnId, rma, orderNumber, customerId, requestedAt, itemCount,
  units, refundMethod, flagReason}]`; approve/reject apply only to PENDING_REVIEW (reject needs `{reason}`).
- Dashboard `GET /manager/dashboard?from&to` → `{returnRateByCategory[{category, returnable, soldUnits,
  returnedUnits, returnRate}], topReasons[{reasonCode, count}], cycleTime{closedReturns, averageHours}, flaggedCustomers[...]}`.
  Returned units exclude CANCELLED returns; return rate covers orders placed in the range; reasons cover
  returns requested in the range; cycle time covers REFUNDED/REJECTED returns closed in the range; flagged
  customers are all active (uncleared) flags, emails masked.
- `GET /manager/audit?entityId=` returns up to 500 rows for a return UUID or refund id, oldest first.
- Label QR codes are rendered at error-correction level Q and decoded once before being issued (fallback H):
  testing showed ~1% of symbols at a fixed level could not be detected by ZXing.

**Authentication (Phase 3):** customers send `Authorization: Bearer <accessToken>` (token → `shared.CustomerPrincipal(orderId)`;
any order/return outside that order → 404). Staff use HTTP Basic against `staff_user` (BCrypt), roles map
`/warehouse/**`→WAREHOUSE, `/finance/**`→FINANCE, `/manager/**`, `/admin/**`→MANAGER, `/staff/**`→any staff role. Missing/expired
credentials → 401 `UNAUTHORIZED`; wrong role → 403 `FORBIDDEN` (both ProblemDetail). Session lookup limits:
`app.session.max-attempts` (5) per `app.session.attempt-window` (1 m) per client IP and per order number
(IP checked first); token TTL `app.session.token-ttl` (2 h).

**Error codes:** ORDER_NOT_FOUND 404, RETURN_NOT_FOUND 404, REFUND_NOT_FOUND 404, UNAUTHORIZED 401, ITEM_NOT_RETURNABLE 422, VALIDATION_FAILED 400, PHOTO_INVALID 400, LABEL_INVALID 400, INVALID_TRANSITION 409, CONCURRENT_MODIFICATION 409, RATE_LIMITED 429, FORBIDDEN 403, GATEWAY_PENDING 202.

**Eligibility microcopy:**
- `CATEGORY_NOT_RETURNABLE`: "For hygiene and safety reasons, {category} items can't be returned."
- `WINDOW_EXPIRED`: "The {n}-day return window for this item closed on {date}."
- `NOT_DELIVERED`: "You can start a return once this item is delivered."
- `ALREADY_IN_RETURN`: "All units of this item are already part of a return."
- `ELIGIBLE`: "Returnable until {date} ({d} days left)." — "1 day left" when d = 1, "last day" when d = 0.
- Dates render as `d MMM yyyy` (e.g. "15 Dec 2026"); `deadline` = delivery date (IST) + window.
- Per-line eligibility is computed in one place, `order.OrderEligibilityService`, for both the order view
  and return creation; already-returned units come from the `order.ReturnedQuantities` port (implemented
  by `returns`).

## 5. Gateway port (`gateway-api`)
```java
public interface PaymentGateway {
  PaymentResult pay(PaymentRequest req);            // idempotent by req.idempotencyKey()
  Optional<PaymentResult> status(String idempotencyKey);
}
```
`gateway-mock` persists results by key, so a repeated key returns the original txn and never charges twice. Fault injection and simulated latency live here.

## 6. Observability
Micrometer metrics:
- `returnright_refund_total{outcome=success|failure|unknown}`
- `returnright_gateway_latency` (Timer, with percentiles)
- `returnright_refund_pending` (gauge)

Exposed at `/actuator/prometheus`. Grafana gets a provisioned dashboard. Prometheus has alert rules for success rate < 95% over 5 m and gateway p95 > 2 s over 5 m.
